# API documentation

Base path: `/api/v1`. OpenAPI JSON: `GET /api/v1/openapi.json`. Authentication uses an HTTP-only access cookie and a rotating refresh cookie; send browser requests with credentials. JSON success/error envelopes are documented in [architecture.md](architecture.md). All write routes validate inputs with Zod.

## Auth and profile

| Method | Path | Access |
|---|---|---|
| POST | `/auth/register` | Public; only CUSTOMER or PHARMACY_OWNER can self-register |
| POST | `/auth/login` | Public, rate limited |
| POST | `/auth/refresh` | Refresh cookie |
| POST | `/auth/logout` | Public, revokes matching refresh token |
| POST | `/auth/forgot-password` | Public, rate limited; enumeration-safe message |
| POST | `/auth/reset-password` | One-time reset token, consumed atomically; revokes existing sessions |
| POST | `/auth/verify-email` | One-time verification token, consumed atomically |
| POST | `/auth/resend-verification` | Authenticated, one-minute cooldown; replaces previous token |
| GET/PATCH | `/auth/me` | Authenticated; own profile |
| GET/PUT | `/users/me/settings` | Authenticated; own profile, saved locations and search preferences |

`GET /users/me/settings` returns `data: { revision, name, email, phone, locations, preferences }`. `PUT` accepts the complete object excluding the read-only `email`; unknown fields are rejected. `phone` may be null to remove the phone number. `locations` accepts up to ten `{ id?, label, pinCode?, latitude?, longitude?, isDefault }` entries, with at most one default. Use an existing location ID to edit it, omit the ID to create one, and omit an entry from the list to remove it. Coordinates must be supplied as a pair in valid latitude/longitude ranges; each location needs a six-digit PIN or coordinates. Locations are stored as GeoJSON `[longitude, latitude]` and are only returned to their account owner.

`preferences` requires `{ searchRadiusKm: 1..50, searchView: "list" | "map", recordSearchHistory: boolean }`. The current `revision` is mandatory; stale saves return `409 SETTINGS_CONFLICT` without overwriting the account. Setting `recordSearchHistory` to false deletes the account's previous searches in the same transaction. Subsequent authenticated searches respect this choice. Account search recording and privacy mutations serialize through an account write, so a concurrent search cannot undo opt-out deletion. Settings GET/PUT use `Cache-Control: no-store`. The profile screen is `/profile`; search applies the saved default location, radius and view when opened.

## Role and account access administration

- `GET /admin/roles` is restricted to SUPER_ADMIN and returns the seven built-in role policies, their revisions, current/default/allowed/fixed permissions and the implemented permission catalogue. `PUT /admin/roles/:code` accepts `{ revision, permissions: string[], reason }`. The reason must contain 5–500 characters. SUPER_ADMIN is immutable; a role cannot receive permissions outside its source-defined ceiling, and basic customer search/profile/own-reservation access cannot be removed. Unknown roles, unknown permissions and stale revisions are rejected. Changes take effect on the next authenticated request; already-running requests may finish under their initial permission snapshot.
- `GET /admin/users?q=...&page=...&limit=...` requires `user:read` and returns `{ users, total, page, limit }`, including `accessRevision` for each account. `limit` is 1–100 (default 25). `PATCH /admin/users/:id/access` requires `user:roles:manage` and accepts `{ revision, roles, active?, reason }`. If `active` is supplied it also requires `user:manage`. `PATCH /admin/users/:id/active` requires `{ revision, active, reason }` and `user:manage`. Use the account's `accessRevision` as `revision`; legacy absent revisions count as zero.
- Only SUPER_ADMIN can appoint, edit or suspend ADMIN, SUPPORT_ADMIN or SUPER_ADMIN accounts. New administrator roles require an active account with verified email and cannot be given to demo accounts. Administrators cannot change their own access. Active pharmacy assignments and pharmacy ownership must retain their matching account roles. Cross-administrator mutations serialize through a database control record; at least one active super administrator must remain. The service rechecks the acting administrator inside the transaction.
- Account access changes increment both the access revision and authentication version, clear refresh/reset tokens, and commit an audit record and in-app notification together. Access and refresh sessions are revoked; local connected sockets are disconnected after commit. Role policy changes preserve existing sessions but every new API request reloads effective permissions from MongoDB. Responses never accept client-provided permissions as authority. The screens are `/admin/users` and `/admin/access`.

## Discovery, pharmacies and catalogue

- `GET /search?q=...&medicineId=...&lat=...&lng=...&radiusKm=...&pinCode=...&sort=distance|price|freshness&availability=all|reservable&freshness=...&page=...&limit=...` searches up to eight terms across name, brand, generic name, composition, manufacturer, strength, form and aliases. `medicineId` selects an exact catalogue item. Price sorting rejects multi-medicine result sets to avoid comparing incompatible products. Coordinates are optional and must be supplied together. Only recent, non-demo availability can be requested. Results use database-side availability aggregation and pagination; `availableQuantity` is omitted when the pharmacy uses range display.
- `GET /search/suggestions?q=...` offers up to ten partial matches. For a single alphabetic term with no partial matches, it may score the catalogue through a bounded MongoDB query and wall-clock deadline, marked `matchType: approximate`. Approximate matches are never searched automatically; the user must select one and confirm its details. Demo catalogue entries remain excluded unless demo discovery is enabled. This is not a dedicated search index and may time out on a large catalogue.
- `GET /search/history` requires authentication and returns up to 20 of the current user's recorded searches, newest first. `DELETE /search/history` clears only that account's history and writes an audit event without search contents. Clearing history does not disable future recording; use the settings preference to opt out. Account search history has a one-year TTL.
- `GET /medicines?q=...&page=...&limit=...` and `GET /medicines/:id` are public catalogue read APIs.
- Public catalogue reads also accept `categoryId` and return only active entries and active category summaries. `GET /medicine-categories?q=...&page=...&limit=...` lists active categories. Pagination is validated (`page` 1–10,000, `limit` 1–100); catalogue matching includes name, brand, generic/composition, strength, form, manufacturer, pack and aliases. Hidden demo medicines and inactive medicines return 404 on the detail route. Public medicine responses use a field allowlist, omit internal editor/reviewer IDs, and include explicit demo markers.
- A public classification is `UNVERIFIED` unless the stored review flag, source reference, review date and reviewing actor are present. Verified public records include the source reference and review date. Legacy classification values without review evidence are not treated as verified. `/medicines/:id` in the client displays the identity and a link to availability search for that exact medicine ID.
- `GET /search?medicineId=...` can search an exact catalogue identity without `q`; when no medicine ID is supplied, `q` is required and retains the normal length/word-count validation. Exact-ID links do not fall back to broad text matching if the entry is missing, inactive or hidden.
- `POST /pharmacies` creates an owner-assigned draft. `POST /pharmacies/:id/license-document` accepts one private PDF/JPEG/PNG multipart field named `document`. `PATCH /pharmacies/:id/submit` submits the owner's draft. `GET /pharmacies/mine` returns assigned pharmacies. `GET /pharmacies?pinCode=...` returns public approved pharmacies.
- `GET /pharmacies/:pharmacyId/staff` lists active and revoked assignments for the assigned owner. `POST` on the same path adds an existing active account by email or restores its revoked assignment. `PATCH /pharmacies/:pharmacyId/staff/:staffId` edits role and permissions; `DELETE` revokes access idempotently. Owner assignments cannot be edited or revoked here. Each mutation commits assignment changes, pharmacist links, audit records and notifications together. Allowed staff permissions are `inventory:read`, `inventory:update`, `reservation:read`, and `report:read`; pharmacist professional privileges depend on independent administrative verification. `/pharmacies/mine` includes effective capabilities for each current assignment.

## Inventory and reservations

- `GET /inventory?pharmacyId=...&page=...&limit=...&q=...&stockStatus=AVAILABLE|UNAVAILABLE&freshness=...&sort=updated_desc|updated_asc` requires an authorized pharmacy assignment and returns filtered batch details and freshness based on configured thresholds. Search covers the central medicine name, brand, generic/composition, manufacturer, strength, dosage form and aliases. `GET /inventory/movements?pharmacyId=...&page=...&limit=...` returns stable descending movement pages with a total count (default 25, maximum 100).
- `POST /inventory/batches` creates a dated batch and stock movement. `PATCH /inventory/batches/:id/quantity` applies a guarded correction. `PATCH /inventory/batches/:id` edits expiry and price details. `PATCH /inventory/:id/status` marks a medicine available/unavailable. `PATCH /inventory/:id/threshold` updates per-medicine low-stock/reorder thresholds and alert enablement. Movement history uses the paginated route described above.
- `POST /inventory/import/preview` accepts multipart fields `file` and `pharmacyId`; CSV/XLSX headers are `medicineId,batchNumber,expiryDate,quantity,sellingPrice,mrp` with optional `manufacturer`. It returns valid-row counts and row errors without modifying stock. `POST /inventory/import/:jobId/confirm` requires `{ "confirm": true }`; only valid rows are imported, and rejected errors are returned. Preview expires after one hour. XLSX accepts one visible worksheet without merged cells, formulas or links; the upload limit is the smaller of the configured limit and 5 MiB, and the limit is 5,000 data rows. `GET /inventory/import/template.xlsx` supplies a blank template.
- `PATCH /pharmacies/:id/opening-hours` updates a seven-day schedule and optional customer contact details for an assigned owner.
- `/saved-pharmacies` lists, saves and removes the authenticated customer's approved non-demo pharmacy favorites.
- `POST /reservations` accepts `{ pharmacyId, medicineId, quantity, notes? }`; an optional nonblank `Idempotency-Key` header prevents duplicate creation for that customer/key. Requests without a key are not constrained by the idempotency index.
- `GET /reservations?page=...&limit=...&status=...` returns the caller's requests; adding `?pharmacyId=...` requires an assignment and returns that pharmacy's requests. Platform administrators with `reservation:read:any` can browse the platform list in `/admin/reservations`.
- `PATCH /reservations/:id/status` accepts `{ status, note?, reviewAttestation? }`. A pharmacist confirming a pending request must supply `{ reviewAttestation: { stockReviewed: true, prescriptionRequirementsReviewed: true } }`; the acknowledgement is recorded in the reservation history and does not contain a prescription. Customer may cancel their own request. Pharmacy owner or an admin/verified assigned pharmacist performs pharmacy transitions. Valid transitions are checked server side.

## Administration, reporting and service modules

### Catalogue administration

`/admin/catalogue` is the administration screen. All catalogue and category write/read administration APIs require the effective `medicine:manage` permission. `GET /admin/medicines?q=...&active=all|true|false&categoryId=...&page=...&limit=...` returns medicines with `revision`, category references/summaries and `identityLocked`; `GET /admin/medicines/:id` returns one administrative entry. Admin reads include inactive and demo records and use `Cache-Control: no-store`.

`POST /admin/medicines` creates an entry. `PATCH /admin/medicines/:id` saves the complete editor form and requires its current `revision`. Both require an audit `reason` of 5–500 characters and the fields `name`, `strength` and `dosageForm`. Send all editable fields: `name`, `brand`, `genericName`, `composition`, `strength`, `dosageForm`, `manufacturer`, `packSize`, `aliases`, `categoryIds`, `prescriptionClass`, `classificationVerified`, `classificationSource`, and `active`. Omitted optional fields receive defaults; these endpoints are not JSON Patch. Aliases allow up to 30 plain-text values, deduplicated without regard to case. Category links allow up to ten IDs; new links must target existing active categories, while an existing archived link may be retained.

Marking a classification verified requires a class other than UNVERIFIED and a source reference of at least five characters. The server records the reviewer and date; these metadata fields cannot be supplied by the client. Changing or withdrawing a review preserves the previous classification/source in the audit metadata. Demo entries cannot be marked verified. Source references are shown publicly for verified records and must not contain private/patient details. This is a manual catalogue review workflow; no external regulatory database is connected.

Medicine identity fields (name, brand, generic name, composition, strength, form, manufacturer and pack) become immutable once the entry has inventory or reservation references. Aliases, categories, review and active state remain editable. First stock creation/import and catalogue editing serialize through a write to the medicine document. Imports also record the catalogue revision in their previews and reject confirmation after a catalogue change. Legacy stock/history references also lock identity. Deactivation hides future public discovery without deleting stock or reservation history. Errors include `409 CATALOGUE_CONFLICT`, `409 MEDICINE_IDENTITY_LOCKED` and `409 CATALOGUE_CHANGED`; create a separate entry for a different product.

`GET /admin/medicine-categories?q=...&active=all|true|false&page=...&limit=...` lists categories. `POST /admin/medicine-categories` accepts `{ name, description?, active?, reason }`. `PATCH /admin/medicine-categories/:id` saves the complete form with its current `revision`. Names are unique after NFKC normalization, whitespace collapsing and lowercasing. Archive/reactivate by changing `active`; archive hides public category metadata while retaining references. Category changes commit with audit records, use revision conflict checks and have no destructive delete endpoint. OpenAPI documents these route contracts.

- `/admin/overview`, `/admin/pharmacies`, `/admin/pharmacies/:id/verification`, `/admin/pharmacies/:id/license-document`, `/admin/users`, `/admin/users/:id/active`, `/admin/medicines`, `/admin/medicines/:id`, `/admin/audit-logs`, `/admin/reservations` require their mapped permissions.
- `/admin/settings` is SUPER_ADMIN-only and reads/updates inventory freshness, reservation hold and pickup thresholds.
- `POST /pharmacists/application` submits registration/council details for a user with an active pharmacist assignment and returns the profile to pending. Submitting a new application clears previous evidence and verification. `GET /pharmacists/me` returns the applicant profile and review history. `POST /pharmacists/me/evidence` uploads private PDF/JPEG/PNG registration evidence as multipart `document`; `GET /pharmacists/me/evidence` lets the applicant download it. Admin reviewers use `GET /pharmacists` and `GET /pharmacists/:id/evidence`, then `PATCH /pharmacists/:id/verification` with `{ status, revision, reason? }`. Rejection or revocation requires a reason; verification requires pending status and existing evidence. An administrator cannot review their own application. The revision changes on submission, evidence upload and review, so stale review attempts return 409. Verification and audit/notification writes use a MongoDB transaction.
- `/notifications`, `/notifications/:id/read`, `/notifications/read-all` are user scoped.
- `POST /support` creates a ticket with subject, category, priority, optional visible/assigned pharmacy and initial message. `GET /support?scope=mine|all&page=...&limit=...&status=...&priority=...&category=...&assignedTo=me|unassigned|<id>` lists scoped summaries; only support managers can view all or filter assignments. `GET /support/:id` returns a scoped conversation and status history. `POST /support/:id/comments` appends a message; a requester reply reopens resolved/closed tickets or moves waiting tickets to open. Support staff reopen resolved/closed tickets before replying. Conversations are limited to 500 messages. Ticket creation and comments use MongoDB-backed shared per-account rate limits.
- `GET /support/agents` lists active support managers for authorized reviewers. `PATCH /support/:id/status` requires the current `revision` and accepts status, priority, `assignedTo` (active support user ID or null), and/or resolution notes. Resolving/closing requires notes; reopening clears the current notes while retaining the previous resolution in history. Stale revisions return 409. Ticket, audit and notification writes are transactional, requiring a replica set. Notifications contain a ticket link and generic text rather than the conversation content.
- `/reports/inventory.csv?pharmacyId=...`, `/reports/inventory.xlsx?pharmacyId=...`, `/reports/stock-movements?pharmacyId=...&from=...`, `/reports/reservations?pharmacyId=...` provide scoped pharmacy exports/aggregates. Exports include at most 25,000 batches; CSV exports neutralize spreadsheet formula prefixes in text, mark demo records, and show zero public available quantity for unavailable, inactive or expired stock.
- `/reports/analytics/pharmacy/overview`, `/inventory`, `/batches`, `/movements` and `/reservations` under the same `/reports/analytics/pharmacy` prefix require an active authorized assignment and `pharmacyId`. Date filters `from` and `to` are inclusive UTC calendar days, limited to 366 days; `medicineId` and reservation `status` are optional. Inventory and batch metrics are current snapshots; date/status filters affect reservation or movement events as labelled. Inventory supports `lowStock=true`; batches support `kind=all|expiring|expired` and `days=1..365`. Detail endpoints accept `page` and `limit` and omit customer identities and notes.
- `GET /reports/analytics/admin/overview` requires platform report permission and accepts the same date, pharmacy, medicine and reservation-status filters. It excludes demo records. User registrations and authenticated search activity are omitted where they cannot be attributed to a selected pharmacy, medicine or status. Search counts include repeat/filter requests. Search-user counts are suppressed below five distinct users; medicine request groups are suppressed below five distinct requesters. Suppression reduces small-cohort disclosure but is not a formal anonymization guarantee. Metrics describe reported activity, not sales.
- `GET /reports/analytics/admin/pharmacies?q=...&page=...` requires platform report permission and returns a minimal non-demo pharmacy directory for report filtering (50 results per page). It does not require pharmacy-review permission.

## Privacy, verification and operations

- `GET /users/me/phone-verification` returns saved-number verification state. `POST` to the same path accepts `{ consent: true, channel: "sms" | "whatsapp" }`; `POST /users/me/phone-verification/check` accepts `{ revision, code }`. The saved number must first be set in profile settings. These endpoints verify the saved number only and do not authenticate a session or establish legal identity. Twilio credentials are required when the provider is enabled; the console code is available only in development.
- `GET /users/me/deletion-request` returns the caller's latest request. `POST` accepts `{ password, confirm: "DELETE MY ACCOUNT" }`; `POST /users/me/deletion-request/cancel` cancels an open request. Requests can be held, rejected or erased by the super-administrator privacy workflow.
- `GET /admin/privacy-requests?status=...&page=...` and `POST /admin/privacy-requests/:id/review` require `privacy:manage` (super-admin only). Review accepts `{ revision, decision: "HOLD" | "REJECTED" | "ERASE", reason }`. Erasure is blocked while professional ownership/staff records, active reservations, unresolved tickets or holds remain; retained records are described in [operations and delivery](operations-and-delivery.md).
- `PUT /admin/retention-holds/:id` requires `privacy:manage` and accepts `{ hold, revision, reason }`. It places/releases a support-content retention hold with an audit record.
- `GET /admin/operations` is super-admin only and returns sanitized email delivery, job lease, support fan-out, notification-stream and provider/retention status. It never returns delivery bodies or credentials.
- Pharmacy review uses `PATCH /admin/pharmacies/:id/verification` with `{ revision, status, reason }`. Only documented state transitions are accepted; approval requires private licence evidence and the reviewer cannot review their own pharmacy.

The OpenAPI path/method inventory matches the registered route families. Some operations still have skeletal request/response schemas; this guide provides their contracts but is not a complete per-field generated schema. No batch-delete route is provided because inventory history is retained.

## Audit history and account details

The `/admin/audit` screen calls `GET /admin/audit-logs`. Require `audit:read` plus one or more `audit:read:<family>` grants. Families are `security` (auth/user/role/settings/audit actions), `pharmacy` (pharmacy/pharmacist/inventory/reservation), `catalogue` (medicine/medicine_category), `support`, `reports` (report actions), and `system` (other prefixes). Unknown actions fall into the super-only system group. Filters and suggestions never expand the caller's scope.

Accepted query fields: inclusive UTC `from`/`to`, exact `action`, `family`, `actorId`, `pharmacyId`, `resourceType`, `resourceId`, `limit` (1–100, default 25), and opaque `cursor`. IDs must be 24 hexadecimal characters. Unknown keys are rejected. Default range is the latest 30 days ending today; a supplied `to` anchors the default start. Maximum interval is 366 days, ending no later than today. Dates are UTC; the UI displays event times in the browser's local timezone.

The success envelope contains `data.logs`, `currentCursor`, `nextCursor` (null at the end), `snapshotAt`, `period`, `limit`, `canViewDetails`, and `canViewIp`. Summaries contain event ID, action, group, timestamp, actor ID (or null), optional actor name, pharmacy ID and resource type/ID. Actor names require `user:read`; lists never contain metadata or IP addresses. Ordering is descending creation time then ID. Signed cursors retain a time cutoff, expire after one hour, and bind to caller, normalized filters, page size and permitted groups. Tampering, expiry or reuse with changed scope/filters returns `400 INVALID_AUDIT_CURSOR`; refresh without a cursor. Ordinary new appends do not shift existing pages. This is not a transaction snapshot: direct backdated writes or clock skew can affect it.

`GET /admin/audit-logs/options` accepts the same filters except cursor and returns permitted `families`, matching `actions`, `resourceTypes`, `optionsLimited`, `period`, and detail/IP flags. Each suggestion list is capped at 200; exact entries can still be typed. Requesting a forbidden family or action returns 403. The options endpoint does not create an audit event.

`GET /admin/audit-logs/:id` returns `data.event` with summary fields and separately permitted detail fields. Out-of-scope and absent records both return 404. `audit:read:details` enables bounded metadata projected through an event-group allowlist. Known credential, private-path, contact and support-conversation keys are excluded, including nested keys; strings are capped at 1,000 characters, arrays at 50 entries, objects at 100 keys, and nested depth at five. Permitted free text may still contain personal information; projection is not semantic anonymization. `audit:read:ip` enables the recorded IP address and is super-only. There is no raw metadata, edit or delete API. List and detail reads record audit events; all audit responses use no-store.

`/admin/users/:id` links from user access and audit actors. Its `GET /admin/users/:id` API requires `user:read`, returns account name/email/phone, roles/status, verification and record timestamps, demo marker and access revision, and excludes credentials, private locations and searches. Assignment summaries additionally require `pharmacy:review` or `pharmacy:manage`; otherwise both `assignments` and `assignmentTotal` are null. Assignment pagination uses `page` (1–10,000) and `limit` (1–50, default 10), includes revoked records, and orders active first then newest creation time/ID. Reads are audited and no-store. Activity links show only the audit groups independently allowed for the viewer; absence of an event is not proof that an action never occurred.
